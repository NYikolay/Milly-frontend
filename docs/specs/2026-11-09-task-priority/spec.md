> Примечание: в названиях фреймов Figma опечатка «Изминение»; в UI

## 1. Контекст и цель

В `2026-11-08-task-detail` строка «Приоритет» карточки свойств была
неинтерактивной, а редактирование приоритета — вне scope. В
`2026-11-09-task-due-modal` и `2026-11-09-task-reminders-page` строки
«Срок» и «Напоминание» стали точками входа в свои экраны. Теперь по
фреймам Figma реализуется отдельная страница выбора приоритета задачи.

Страница открывается из строки «Приоритет» на `/tasks/:id` и позволяет
выбрать один из четырёх приоритетов матрицы Эйзенхауэра. Выбор сразу
применяется через `PATCH /tasks/{id}` и возвращает пользователя на
`/tasks/:id`; отдельной кнопки сохранения нет. Новых серверных контрактов
не требуется: `PATCH /tasks/{id}` уже принимает `priority`.

## 2. Пользовательские сценарии

1. Пользователь открывает `/tasks/:id`, нажимает строку «Приоритет».
   Открывается `/tasks/:id/priority`: заголовок «Приоритет задачи»,
   подсказка «Выберите приоритет задачи по Матрице Эйзенхауэра»,
   карточка из четырёх вариантов с отметкой текущего приоритета и
   пояснение про матрицу Эйзенхауэра.
2. Пользователь выбирает другой приоритет. Сразу отправляется
   `PATCH /tasks/{id}` с `{ "priority": ... }`, приложение возвращается
   назад на `/tasks/:id`, где значение приоритета обновляется
   оптимистично; после ответа кэш деталей и списков ревалидируется.
3. Пользователь выбирает уже установленный приоритет. Запрос не
   отправляется, приложение просто возвращается назад: состояние не
   изменилось.
4. `PATCH` завершился ошибкой, кроме `404`. Пользователь уже вернулся на
   детали; оптимистичное значение откатывается, звучит error haptic и
   показывается toast «Не удалось изменить приоритет. Попробуйте ещё
   раз.».
5. `PATCH` завершился `404`. Задача исчезла; детальный кэш
   инвалидируется, маршрут деталей сам показывает «Задача не найдена».
6. Пользователь возвращается системной кнопкой Telegram или историей
   браузера, не выбирая вариант. Приоритет не меняется.
7. Пользователь открыл `/tasks/:id/priority` напрямую или обновил
   страницу. Пока идёт bootstrap/auth — скелетон; после авторизации —
   загрузка задачи. Невалидный `id` — «Задача не найдена» без запроса;
   `404` — «Задача не найдена»; другая ошибка — «Не удалось загрузить
   задачу» и «Повторить».
8. SSR-ответ `/tasks/:id/priority` не содержит защищённых данных задачи;
   только скелетон.

## 3. Функциональные требования

### FR-1. Маршрут и навигация

- Добавить маршрут `tasks/:id/priority` в `app/routes.ts` внутри
  `layout("routes/_app.tsx", [...])` после `tasks/:id/reminders`:
  - `route("tasks/:id/priority", "routes/task-priority.tsx")`.
- Route-модуль `app/routes/task-priority.tsx`:
  - `meta`: `title` — `Приоритет — Milly`, `description` —
    `Изменение приоритета задачи в Milly`;
  - без loader/action: данные загружаются React Query после `AuthGate`;
  - `id` читается через `useParams<{ id: string }>()`;
  - невалидный `id` (`Number.isSafeInteger(id) === false` или `id <= 0`)
    показывает «Задача не найдена» без запроса;
  - `useTaskDetail(taskId, isValidId)` — тот же ключ
    `["tasks","detail",taskId]`, что и на деталях.
- Нижняя навигация: активна вкладка «Задачи» (в Figma активна
  «Главная» — артефакт копирования фреймов, как в других экранах задач).
  FAB добавления задачи не показывается.
- Возврат назад:
  - в Telegram показывается нативная `BackButton` (Bot API 6.1+,
    `useTelegramBackButton`);
  - `navigate(-1)`, если `shouldGoBack(window.history.state)`; иначе
    `/tasks/{taskId}`, а для невалидного `id` — `/tasks`;
  - `BackButton` скрывается при размонтировании;
  - отдельная видимая кнопка «Назад» в контент не добавляется.
- Экран прокручивается вертикально; нижняя навигация фиксирована.

### FR-2. Данные, API и кэш

- `TaskUpdateInput` в `app/lib/tasks/types.ts` расширяется:
  - `priority?: Priority`.
- Мутация `useUpdateTaskPriority(taskId)` в
  `app/hooks/use-update-task-priority.ts`:
  - `mutationFn: (priority: Priority) => updateTask(taskId, { priority })`;
  - перед запросом оптимистично обновляется детальный кэш:
    `priority` задачи меняется сразу, снимок сохраняется для отката;
  - `onMutate` отменяет текущие запросы детального ключа;
  - ошибка (кроме `404`): снимок возвращается, error haptic, toast
    «Не удалось изменить приоритет. Попробуйте ещё раз.»;
  - ошибка `404`: снимок возвращается, error haptic, детальный ключ
    инвалидируется (маршрут покажет «Задача не найдена»); отдельный
    toast не показывается;
  - успех: если `updated.id === taskId`, детальный кэш заменяется
    ответом backend; success haptic;
  - `onSettled`: инвалидация `["tasks","detail",taskId]`, `["tasks"]`,
    `["task-series"]`; проекты не инвалидируются, потому что приоритет
    не влияет на прогресс проектов;
  - ответ PATCH может представлять другой экземпляр серии, поэтому
    детальный ключ всегда инвалидируется, а не только перезаписывается.
- Чистый помощник `applyTaskDetailPriority(task, priority)` в
  `app/lib/tasks/task-detail-cache.ts`:
  - возвращает исходную задачу, если данных нет или приоритет не
    изменился;
  - иначе возвращает копию с новым `priority`.
- Запросы идут через существующий `updateTask` / `apiRequest`.

### FR-3. Заголовок и пояснение

- Контент страницы: тот же каркас, что у деталей:
  `flex flex-1 flex-col gap-2 px-4` с
  `paddingBottom: CONTENT_BOTTOM_PADDING`.
- Блок заголовка: `px-[15px] py-[15px]`, `h1` `24px`, Bold,
  `line-height: 29px`, `letter-spacing: -0.8px`, `app-text`,
  перенос по словам, текст «Приоритет задачи».
- Подсказка под заголовком: `px-[15px]`, `13px`, Regular,
  `line-height: 1.4`, `app-text-secondary`, текст
  «Выберите приоритет задачи по Матрице Эйзенхауэра».
- Между блоками — `8px` (root `gap-2`).

### FR-4. Карточка вариантов

- Карточка: `app-card`, радиус `25px`, внутренние отступы `15px`,
  `role="radiogroup"` с `aria-label="Приоритет задачи"`.
- Четыре строки строго в порядке `PRIORITY_OPTIONS`:
  1. «Срочные и важные» → `urgent_important`;
  2. «Важные, но не срочные» → `important_not_urgent`;
  3. «Срочные, но не важные» → `urgent_not_important`;
  4. «Не срочные и не важные» → `neither`.
- Строка:
  - высота `47px`, ширина на всю карточку;
  - `button` с `type="button"`, `role="radio"`,
    `aria-checked={option.value === task.priority}`;
  - ведущая ячейка `24×24`, в выбранной строке — иконка `check.svg`
    цвета `app-accent`, в невыбранной — пустое место того же размера;
  - текст `15px`, `line-height: 1.3`, `app-text`, `truncate`;
  - промежуток между отметкой и текстом `11px`;
  - разделитель `1px app-stroke` под текстовой частью каждой строки,
    кроме последней (как в Figma: линия начинается после отметки);
  - focus-стили `outline-2` `app-accent` с отрицательным offset и
    `active:opacity-70`.
- Нажатие на строку:
  - haptic selection;
  - если приоритет отличается — вызывает `onSelect(priority)`
    (мутация + возврат назад по FR-1);
  - если приоритет тот же — возврат назад без `PATCH`.
- Pending-состояние не показывается: после выбора сразу выполняется
  переход назад.
- Завершённая задача тоже может менять приоритет: отдельного запрета
  нет.

### FR-5. Пояснение про матрицу

- Под карточкой — текст `px-[15px]`, `13px`, Regular,
  `line-height: 1.4`, `app-text-secondary`:
  «Матрица Эйзенхауэра - это простой и полезный метод
  тайм-менеджмента. Он помогает расставить приоритеты и разделить дела
  по двум главным признакам: важность и срочность.»
- Перенос строк естественный; блок не является ссылкой и не
  интерактивен.

### FR-6. Состояния загрузки и ошибок

- `TaskPrioritySkeleton`:
  - `role="status"`, `aria-busy="true"`,
    `aria-label="Загружаем приоритет"`;
  - повторяет геометрию: заголовок в 1–2 строки, подсказка, карточка
    `218px`, блок пояснения в 2–3 строки.
- Route при `isPending` показывает скелетон; при ошибке без кэша —
  существующий `TaskDetailError`:
  - `404` → «Задача не найдена» с «Назад»;
  - прочее → «Не удалось загрузить задачу» с «Повторить» (`refetch`).
- Если данные уже есть, фоновый refetch не скрывает экран.
- `RouteSkeleton` определяет путь
  `/^\/tasks\/[^/]+\/priority\/?$/` и рендерит `TaskPrioritySkeleton`
  вместо `TaskDetailSkeleton`.
- Ошибки `PATCH` не блокируют переход назад и показываются toast’ом
  (кроме `404`, где работает экран «Задача не найдена»).

### FR-7. Строка «Приоритет» на деталях

- `TaskDetailCard` получает необязательный проп
  `onPriorityClick?: () => void`.
- Если обработчик передан, строка «Приоритет» рендерится кнопкой с
  `aria-label="Изменить приоритет"`; без обработчика остаётся
  неинтерактивной, как раньше.
- `TaskDetailView` получает и пробрасывает `onPriorityClick`.
- В `routes/task-detail.tsx` обработчик вызывает
  `haptics.selection()` и `navigate("/tasks/{task.id}/priority")`.
- Остальные строки карточки не становятся интерактивными.

### FR-8. Темы, доступность и Telegram

- Только токены `app-*`; light/dark через `data-app-theme`, без `dark:`
  и хардкода цветов.
- Все интерактивные элементы — `button` с `type="button"`, доступным
  именем и focus-стилями.
- `role="radiogroup"` / `role="radio"` и `aria-checked` отражают выбор.
- Safe-area учитывается `AppShell`; контент получает нижний отступ
  `CONTENT_BOTTOM_PADDING`.
- Haptics — только через `useTelegram().haptics`:
  `selection()` на возврате/выборе, `notification("success"|"error")`
  по результату `PATCH`.
- Ширины `320 / 412 / 448px`, light/dark и safe-area не ломаются.

- Фон — `app-bg`; карточка — `app-card`.

- Разделители — `app-stroke`; акцент и отметка — `app-accent`.
- Light/dark переключаются только через `data-app-theme`; в Figma
  светлый фон `#f2f2f7`, карточка `#ffffff`, текст `#303033`,
  вторичный `#7a7d83`, акцент `#007aff`; в приложении используются
  соответствующие `app-*`.

### 4.5. Принятые отклонения

- Подписи вариантов берутся из `PRIORITY_OPTIONS` (множественное
  число), а не из Figma (единственное число с опечаткой «Сорочная»),
  чтобы сохранить единый словарь приоритетов приложения.
- Активная вкладка «Главная» в Figma заменяется на «Задачи» — тот же
  артефакт копирования фреймов, что и в спецификациях деталей,
  напоминаний и срока.
- В Figma первая строка отмечена галочкой как пример; в приложении
  отмечается фактический `task.priority`.
- Toast ошибки и оптимистичное обновление в Figma отсутствуют:
  добавлены как необходимое поведение мгновенного выбора и возврата.

## 5. Нефункциональные требования

- TypeScript strict, без `any`; типы — через `import type`.
- Новые зависимости не добавляются; используется существующий
  `sonner` toast через `AppToaster`.
- Все API-запросы — через `apiRequest` / `updateTask`; `fetch` в
  компонентах не используется.
- SSR включён; защищённые данные не попадают в SSR-ответ. `useQuery`
  выполняется только после `AuthGate`.
- Обращений к `window`/`document` на верхнем уровне модулей нет.
- Файлы — `kebab-case`, компоненты — `PascalCase`, алиас `~/*`.
- Линтер не настроен; `npm run lint` не добавлять.
- Тесты — Vitest, среда `node`, без jsdom.

## 8. Принятые решения

1. **Отдельная страница, а не шторка.** Во фреймах — полноэкранный
   макет с нижней навигацией и Telegram-хедером, как у напоминаний.
   Страница живёт на `/tasks/:id/priority`.
2. **Мгновенный выбор без кнопки сохранения.** Нажатие на вариант —
   это и есть подтверждение; кнопки «Применить»/«Готово» нет.
3. **Оптимистичное обновление + немедленный возврат.** Пользователь не
   ждёт сеть на экране выбора: детальный кэш обновляется сразу, переход
   выполняется в том же обработчике, ответ сервера затем ревалидирует
   кэш.
4. **Ошибка после возврата — toast.** Инлайн-ошибка на уже закрытом
   экране бессмысленна, поэтому не-`404` ошибки показываются toast’ом
   и откатывают оптимистичное значение.
5. **`404` — на усмотрение деталей.** Кэш инвалидируется, и экран
   деталей сам показывает «Задача не найдена»; отдельный toast не
   дублирует сообщение.
6. **Текущий приоритет не отправляется.** Если выбран тот же вариант,
   `PATCH` не нужен; выполняется только возврат.
7. **Единый словарь приоритетов.** Используется `PRIORITY_OPTIONS`,
   несмотря на единственное число и опечатку в Figma, чтобы не
   расходиться с быстрым созданием, поиском и карточкой деталей.
8. **Кэш.** Детальный ключ остаётся под `["tasks"]`; после успеха
   инвалидируются `["tasks"]` и `["task-series"]`, потому что PATCH
   экземпляра активной серии применяет изменения к серии и будущим
   экземплярам.
