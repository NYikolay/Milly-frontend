# Milly — экраны ошибок 404/429/5xx (SDD Specification)

**Статус:** draft for approval
**Дата:** 2026-11-03
**Область:** `frontend/`
**Figma:** `52:5848` (404 page light), `52:6170` (404 page dark), `52:5947` (5xx page light), `52:6296` (5xx page dark), `52:6061` (429 page light), `52:6497` (429 page dark)
**Связанные спецификации:** `docs/specs/2026-11-02-home-dashboard/spec.md`, `docs/specs/2026-11-02-telegram-auth/spec.md`, `docs/specs/2026-11-03-bootstrap-budget/spec.md`
**База реализации:** текущее рабочее дерево, включая незакоммиченные изменения bootstrap-бюджета, axios-миграцию и удалённые старые `plan.md`.

## 1. Контекст и цель

Сейчас у приложения нет отдельных экранов для 404, 429 и 5xx:

- unmatched URL попадает в корневой `ErrorBoundary` с английским текстом
  `404` / `Error`, использует `tg-*` токены, не имеет `AppShell`,
  безопасных зон и нижней навигации;
- 429 нигде не выделен: `ApiError` с этим статусом просто пробрасывается
  вызывающему коду;
- 5xx вне auth-сценария не имеет собственного экрана;
- auth-ошибки уже обрабатываются `AuthScreen` и в эту итерацию не входят.

Цель — реализовать полноэкранные состояния ошибок по шести фреймам Figma:

1. `404` — «Страница не найдена»;
2. `5xx` — «Что-то пошло не так»;
3. `429` — «Слишком много запросов».

Экраны должны работать в light/dark через существующие `app-*` токены,
сохранять нижнюю навигацию, давать пользователю основное и вторичное
действия и не требовать новых runtime-зависимостей.

Ошибки валидации форм (400/422 и inline-состояния полей) в эту итерацию
не входят. Глобальный перехват ошибок React Query/API также не входит:
по решению пользователя 429/5xx показываются через route error
boundaries, а не через общий overlay.

## 2. Пользовательские сценарии

1. Пользователь открывает устаревшую или неизвестную ссылку. Показывается
   404-экран с кнопками «На главную» и «Назад». Экран доступен без
   авторизации.
2. Loader/action маршрута получает от backend `429`. Показывается
   429-экран с кнопками «Повторить запрос» и «Назад» и подсказкой
   «Сделайте небольшую паузу».
3. Loader/action получает `5xx`, либо в приложении происходит
   непредвиденная ошибка. Показывается 5xx-экран с кнопками
   «Попробовать снова» и «Назад». Если известен `request_id`, под
   карточкой выводится код ошибки.
4. Пользователь нажимает основную кнопку повтора. Route boundary
   повторно запускает loader/action через revalidation. Если ошибка
   произошла при рендере и revalidation не поможет, страница
   перезагружается.
5. Пользователь нажимает «Назад». Приложение возвращается на предыдущий
   экран. Если истории в приложении нет, открывается главная.
6. Пользователь меняет тему Telegram. Экраны используют `app-*`
   токены и `data-app-theme`; отдельные `dark:`-классы не нужны.
7. Пользователь открывает 404/429/5xx на экране 320 px: текст
   переносится, горизонтального скролла нет, нижняя навигация не
   перекрывает карточку.

## 3. Функциональные требования

### FR-1. Классификация ошибок

Добавляется чистый модуль классификации, не зависящий от React:

```ts
export type AppErrorKind = "not-found" | "rate-limited" | "server";

export interface AppErrorDescriptor {
  kind: AppErrorKind;
  status: number | null;
  requestId: string | null;
}

export interface AppErrorPayload {
  appError: AppErrorDescriptor;
}
```

Правила классификации:

| Вход | `kind` | `status` | `requestId` |
|---|---|---:|---|
| `isRouteErrorResponse(error)` со статусом `404` | `not-found` | `404` | из payload/поля, иначе `null` |
| `isRouteErrorResponse(error)` со статусом `429` | `rate-limited` | `429` | из payload/поля, иначе `null` |
| `isRouteErrorResponse(error)` со статусом `>= 500` | `server` | статус | из payload/поля, иначе `null` |
| `ApiError` со статусом `404` | `not-found` | `404` | `error.requestId` или `null` |
| `ApiError` со статусом `429` | `rate-limited` | `429` | `error.requestId` или `null` |
| `ApiError` со статусом `>= 500` | `server` | статус | `error.requestId` или `null` |
| `ApiNetworkError` | `server` | `null` | `null` |
| любой другой статус `ApiError` | `server` | статус | `error.requestId` или `null` |
| `Error` / неизвестное значение | `server` | `null` | `null` |

- Прочие 4xx (400, 401, 403, 409, 422) не получают отдельного экрана и
  используют generic-вариант `server`; блок «Ошибка на стороне сервера»
  для них не показывается (см. FR-4).
- `requestId` читается из `ApiError.requestId`, из `error.data.appError.
  requestId` (payload `throwAppError`), либо из `error.data.requestId` /
  `error.data.request_id`, если loader бросил `data(...)` вручную.
- Пустая строка `requestId` нормализуется в `null`.

Для loader/action добавляется helper:

```ts
export function throwAppError(error: unknown): never;
```

- Если на вход пришёл уже готовый route error response
  (`isRouteErrorResponse(error)`), helper пробрасывает его без изменений.
- Иначе выбрасывает `data({ appError: descriptor }, { status:
  descriptor.status ?? 500 })`.
- Helper нужен, чтобы `ApiError` со статусом 429/5xx не потерял статус
  при SSR-сериализации: React Router санитизирует обычные `Error` в
  production, но не санитизирует `throw data(...)`.
- Helper не используется в клиентских компонентах и не заменяет
  обработку `401` в `apiRequest`.

### FR-2. 404 — «Страница не найдена»

- Заголовок: `Страница не найдена`.
- Описание: `Возможно, ссылка устарела или страница была перемещена.`
- Основное действие: `На главную` → переход на `/`.
- Вторичное действие: `Назад`.
- Подсказка под карточкой отсутствует.
- Источники:
  - unmatched URL → корневой `ErrorBoundary`; HTTP-статус ответа
    сохраняется `404`;
  - loader/action, которому нужен 404, бросает
    `throwAppError(new ApiError(..., { status: 404, ... }))` или
    `throw data(..., { status: 404 })`;
  - 404 из loader внутри `_app` попадает в `_app` boundary.
- 404 доступна без авторизации: корневой boundary находится вне
  `AuthGate`.

### FR-3. 429 — «Слишком много запросов»

- Заголовок: `Слишком много запросов`.
- Описание: `Вы отправили слишком много запросов подряд. Подождите
  немного и повторите попытку.`
- Основное действие: `Повторить запрос` → повторная попытка.
- Вторичное действие: `Назад`.
- Подсказка под карточкой: `Сделайте небольшую паузу` (без точки, как в
  light-макете).
- `requestId` на 429 не выводится.
- Заголовок `Retry-After` backend в этой итерации не парсится и не
  показывается; отсчёт секунд не реализуется.
- Глобального перехвата 429 из React Query/`apiRequest` нет: экран
  показывается только если 429 дошёл до route error boundary через
  loader/action или `throwAppError`.

### FR-4. 5xx — «Что-то пошло не так»

- Заголовок: `Что-то пошло не так`.
- Описание — два абзаца:
  1. `Не удалось выполнить запрос. Попробуйте ещё раз чуть позже.`
  2. `В случае повторения ошибки пожалуйста, обратитесь в службу
     поддержки.`
- Основное действие: `Попробовать снова` → повторная попытка.
- Вторичное действие: `Назад`.
- Подсказка под карточкой:
  - первая строка всегда: `Ошибка на стороне сервера.`;
  - вторая строка только при непустом `requestId`:
    `Код ошибки: {requestId}`.
- Если `requestId` нет (например, обычный `Error` или `Response` без
  payload), вторая строка не рендерится; пустая строка кода не
  показывается.
- Для `server`-варианта со статусом 400–499 (прочие 4xx) блок
  «Ошибка на стороне сервера.» и код не показываются: это generic-
  состояние, а не подтверждённая серверная ошибка.
- Любая непредвиденная ошибка рендера/загрузки, не являющаяся 404/429,
  использует этот вариант.

### FR-5. Boundaries и интеграция с React Router

- `app/root.tsx` экспортирует `ErrorBoundary`, который рендерит общий
  компонент `AppErrorBoundary`:
  - обрабатывает unmatched URL (404) и ошибки корневого уровня;
  - находится вне `AppProviders`, поэтому не использует `useTelegram`,
    `useAuth`, React Query и haptics;
  - рендерит `AppShell` + error-экран + нижнюю навигацию
    самостоятельными компонентами без провайдеров.
- `app/routes/_app.tsx` экспортирует `ErrorBoundary`, который рендерит
  тот же `AppErrorBoundary`:
  - ловит ошибки дочерних loader/action/рендера;
  - заменяет `AppShell > AuthGate > Outlet`, но сохраняет корневые
    `AppProviders`;
  - поэтому 429/5xx из авторизованной части показываются без потери
    React Query и auth-состояния.
- Отдельный catch-all route не добавляется: unmatched URL обрабатывает
  корневой boundary, сохраняя HTTP `404`.
- Error-экраны не являются route-модулями и не меняют `app/routes.ts`.
- Нижняя навигация:
  - рендерится на всех трёх error-экранах, как в макетах;
  - используется существующий `BottomNavigation` без изменения его
    внешнего вида;
  - активная вкладка — `home`;
  - вкладки не навигируют (поведение как у главного экрана: только
    отображение и haptic в будущем);
  - панель фиксирована снизу, safe-area учитывается так же, как на
    главном экране.
- Действия:
  - «На главную» / основная кнопка 404 — `navigate("/")`;
  - «Назад» — `navigate(-1)`, если в истории React Router есть
    предыдущая запись (`window.history.state.idx > 0`), иначе
    `navigate("/")`;
  - «Попробовать снова» / «Повторить запрос» — `revalidator.revalidate()`
    для route error response, `ApiError` и `ApiNetworkError`;
  - для остальных ошибок (например, исключение при рендере) — полная
    перезагрузка `window.location.reload()`;
  - пока идёт revalidation, основная кнопка disabled и имеет
    `aria-busy="true"`;
  - повторный клик во время revalidation не запускает вторую попытку.
- `window` и `document` не используются на верхнем уровне модулей —
  только в обработчиках и эффектах.

### FR-6. DEV preview

Для ручной проверки 429/5xx без реального backend в `home.tsx` loader
добавляется DEV-only preview, совместимый с существующим
`?state=empty`:

- `import.meta.env.DEV` истинно;
- `?state=429` → `throwAppError(new ApiError("Too many requests", {
  status: 429, code: "rate_limited", requestId: "" }))`;
- `?state=5xx` → `throwAppError(new ApiError("Internal server error", {
  status: 500, code: "internal_error", requestId:
  "preview-5xx-0001" }))`;
- `?state=404` не обязателен: 404 проверяется любым неизвестным URL;
- в production-сборке preview не активен и не влияет на реальные
  данные;
- `?state=empty` сохраняет текущее поведение.

## 4. Данные и состояния

### 4.1. Контракт

```ts
export type AppErrorKind = "not-found" | "rate-limited" | "server";

export interface AppErrorDescriptor {
  kind: AppErrorKind;
  status: number | null;
  requestId: string | null;
}

export interface AppErrorPayload {
  appError: AppErrorDescriptor;
}
```

- `status` — HTTP-статус, если он известен; `null` для сетевых и
  неизвестных ошибок.
- `requestId` — только для отображения в 5xx; не логируется, не
  сохраняется в storage и не попадает в URL.
- `AppErrorPayload` используется только в `throw data(...)` из
  loader/action; клиентские компоненты получают уже готовый
  `AppErrorDescriptor`.

### 4.2. Состояния

```text
route error / render error / unmatched URL
  -> classifyAppError
  -> not-found | rate-limited | server
  -> AppErrorPage
       -> primary: home | retry
       -> secondary: back
```

- Отдельного глобального store/context нет.
- Ошибка не сохраняется между переходами.
- Retry не создаёт новый маршрут: он переиспользует текущий boundary.
- После успешного retry boundary размонтируется, и приложение
  возвращается к обычному экрану.
- При повторной ошибке экран остаётся тем же; кнопка снова доступна
  после завершения revalidation.

### 4.3. Маппинг действий

| `kind` | Primary | Secondary | Retry-стратегия |
|---|---|---|---|
| `not-found` | `На главную` → `/` | `Назад` | не показывается |
| `rate-limited` | `Повторить запрос` | `Назад` | revalidate, иначе reload |
| `server` | `Попробовать снова` | `Назад` | revalidate, иначе reload |

## 5. Визуальная спецификация

Верхний нативный header Telegram (`Milly / мини-приложение`, кнопки
закрытия и меню) на макетах является частью Telegram, а не React-
разметки. Приложение его не дублирует.

### 5.1. Токены

| Элемент | Light | Dark | Токен |
|---|---|---|---|
| Фон страницы | `#F2F2F7` | `#171717` | `app-bg` |
| Карточка | `#FFFFFF` | `#212121` | `app-card` |
| Заголовок | `#303033` | `#FFFFFF` | `app-text` |
| Описание | `#7A7D83` | `#7A7D83` | `app-text-secondary` |
| Подсказка под карточкой | `#7A7D83` | `#7A7D83` | `app-text-secondary` |
| Основная кнопка | `#007AFF` + белый текст | то же | `app-accent` |
| Вторичная кнопка | `#007AFF` | то же | `app-accent` |
| Логотип | оригинальные цвета `Logo.svg` | то же | — |

- Новые токены не добавляются.
- В Figma вторичное действие имеет `#0088FF`, но в приложении
  используется существующий `app-accent` `#007AFF`; разница в 1 px
  канала не является продуктовой и не оправдывает новый токен.
- Подсказка использует `app-text-secondary`, а не более светлый
  `app-hint`, потому что в макете цвет `#7A7D83`.
- `dark:`-классы не используются.

### 5.2. Сетка и контейнер

- Корневой контейнер — существующий `AppShell`: `max-w-md`, safe-area,
  `bg-app-bg`, `text-app-text`.
- Контент error-экрана: `flex flex-1 flex-col` с горизонтальными
  отступами `25px` и верхним отступом `24px`.
- Карточка и подсказка лежат в grid-контейнере
  `grid w-full max-w-[362px] flex-1 justify-items-center` с
  горизонтальным центрированием `mx-auto`.
- Строки grid: при наличии подсказки
  `minmax(0,1fr) auto minmax(57px,1fr)`, без подсказки
  `minmax(0,1fr) auto minmax(0px,1fr)`. Карточка занимает вторую
  строку (`row-start-2`), подсказка — третью (`row-start-3`).
  На коротких экранах (`max-height: 620px`) при наличии подсказки
  третья строка становится `minmax(57px,auto)`: верхняя `1fr`-строка
  схлопывается, и обычный preview-код помещается без прокрутки.
- У `main` нет ограничения `max-height`; у grid-контейнера задан
  `min-height: 0`. На коротких экранах документ растёт по контенту:
  подсказка остаётся в обычном потоке и прокручивается выше
  фиксированной навигации. `min-height: 0` позволяет flex/grid
  распределять свободное место, не блокируя рост документа.
- Подсказка находится в обычном потоке на `15px` ниже карточки.
  Зарезервированная третья строка удерживает подсказку в потоке,
  а `1fr`-строки на высоких экранах сохраняют вертикальное
  центрирование карточки.
- Нижний отступ контента резервирует фиксированную навигацию так же,
  как главный экран:
  `calc(89px + max(0px, 30px - var(--app-inset-bottom)))`.
- На коротких экранах (`max-height: 620px`) вертикальный padding
  карточки уменьшается с `30px` до `20px`. На `320×568` обычный
  preview-код (`preview-5xx-0001`, 16 символов) целиком помещается выше
  верхней границы навигации; более длинные или переносящиеся
  `requestId` остаются доступными прокруткой документа.
- Строки подсказки имеют `max-w-full break-words`, а контейнер
  подсказки — `min-w-0`, поэтому длинный неразрывный `requestId`
  переносится и не расширяет grid-колонку. На коротких экранах
  контент может прокручиваться; горизонтального скролла нет.
- На ширине `320px` карточка сжимается до доступной ширины, текст
  переносится, кнопки остаются шириной 100%.

### 5.4. Карточка

- `width: 100%`, `max-width: 362px`.
- `border-radius: 25px`, `padding: 30px 15px`; на коротких экранах
  (`max-height: 620px`) вертикальный padding — `20px` (см. 5.2).
- `display: flex`, `flex-direction: column`, `align-items: center`,
  `gap: 20px`, `text-align: center`.
- Логотип: `50 × 50px`, `<img>` с `alt=""`, оригинальные цвета.
- Текстовый блок: `display: flex`, `flex-direction: column`,
  `gap: 15px`, ширина 100%.
- Блок описания: `display: flex`, `flex-direction: column`,
  `gap: 15px`; каждый абзац — отдельный `<p>`.
- Блок действий: `display: flex`, `flex-direction: column`,
  `gap: 15px`.
- Высоты карточек при ширине 362 px:
  - 404 — `315px`;

### 5.5. Кнопки

- Основная кнопка:
  - ширина 100%, высота `50px`, радиус `25px`;
  - `background: app-accent`, текст белый, 15 px / 600;
  - `type="button"`;
  - `active:opacity-70`;
  - видимый `focus-visible` outline `app-accent`;
  - в состоянии retry — `disabled` и `aria-busy="true"`.
- Вторичная кнопка «Назад»:
  - текстовая кнопка 15 px / 600 цвета `app-accent`;
  - визуальная высота текста `18px`;
  - кликабельная область не меньше `44px` по высоте; это достигается
    вертикальными отступами/отрицательными margin, чтобы визуальный
    gap между кнопками оставался `15px`, а суммарная высота блока
    действий — `83px`;
  - `type="button"`, видимый focus-visible outline.

### 5.6. Подсказка под карточкой

- Расположена на `15px` ниже карточки, по центру, в обычном потоке
  (не `absolute`) в зарезервированной третьей строке grid-контейнера.
- `display: flex`, `flex-direction: column`, `gap: 5px`,
  `align-self: start`, `min-width: 0`, ширина 100%.
- Текст 13 px / 400, line-height 1.4, цвет `app-text-secondary`.
- Строки подсказки имеют `max-w-full break-words`: длинный неразрывный
  `requestId` переносится и не вызывает горизонтального скролла;
  `min-width: 0` не даёт grid-колонке расшириться по min-content
  длинного слова.
- На коротких экранах третья строка grid использует
  `minmax(57px,auto)`, поэтому подсказка растёт по контенту и
  прокручивается вместе с документом, а не уходит под навигацию.
- 404 — отсутствует.
- 429 — одна строка `Сделайте небольшую паузу`.
- 5xx — одна или две строки: `Ошибка на стороне сервера.` и, при
  наличии, `Код ошибки: {requestId}`.
- На коротких экранах (`max-height: 620px`) уменьшенный padding
  карточки оставляет обычный preview-код выше фиксированной
  навигации; на `320×568` нижняя граница подсказки не пересекает
  верхнюю границу навигации. Более длинные или переносящиеся
  `requestId` доступны прокруткой документа: после прокрутки до низа
  подсказка целиком находится выше навигации. `15px`-отступ и
  центрирование карточки на высоких экранах сохраняются.

### 5.7. Нижняя навигация

- Используется существующий `BottomNavigation` с glass-стилем.
- Высота `65px`, скругление, 4 вкладки; активна `Главная`.
- Панель фиксирована у нижней границы:
  - `position: fixed`, `inset-inline: 0`, `bottom: 0`, `z-index: 20`;
  - нижний отступ `max(30px, var(--app-inset-bottom))`;
  - боковые отступы `var(--app-inset-left/right)`;
  - внутренний контейнер `max-w-md px-4`.
- Вкладки не навигируют; активная вкладка имеет `aria-current="page"`.

## 6. Темы и Telegram

- Экраны используют `app-*` токены и `data-app-theme`, который
  выставляет inline-скрипт в `<head>` и `TelegramProvider`.
- В `_app` boundary тема обновляется через `TelegramProvider`; в
  корневом boundary провайдеров нет, поэтому live-событие
  `themeChanged` там не обрабатывается. Начальная тема задаётся
  inline-скриптом до гидратации; после перехода на главную тема снова
  синхронизируется. Это осознанное ограничение root boundary.
- Верхний нативный header Telegram не рендерится.
- Безопасные зоны применяет `AppShell`; error-экраны не добавляют
  собственные `--app-inset-*`, кроме нижней панели, которая использует
  те же переменные, что и главный экран.
- Haptics на error-экранах не добавляются: root boundary находится вне
  `TelegramProvider`, а экран должен работать без провайдеров.
- `telegram-web-app.js` остаётся в `<head>` до Meta, Links и app-
  скриптов; задача его не перемещает.

## 7. Доступность

- Карточка: `role="alert"`, `aria-labelledby` заголовка,
  `aria-describedby` описания и подсказки.
- Заголовок — `h1` с `tabIndex={-1}`; при mount фокус переходит на
  заголовок.
- Основная и вторичная кнопки — нативные `<button type="button">` с
  доступными именами и видимым `focus-visible` outline.
- Вторичная кнопка имеет hit-area не меньше 44 px, даже если визуально
  это текст 18 px.
- Нижняя навигация: `aria-label="Основная навигация"`, активная
  вкладка — `aria-current="page"`.
- Ошибка передаётся текстом, а не только цветом.
- При `retryPending` основная кнопка disabled и `aria-busy="true"`;
  фокус переносится на заголовок, чтобы disabled-кнопка не «уронила»
  его в `body`.
- На 320 px нет горизонтального скролла и обрезанного текста.

## 8. Нефункциональные требования

- Новых runtime-зависимостей нет.
- TypeScript strict, без `any`; типы — через `import type`.
- Не обращаться к `window`/`document` на верхнем уровне модулей.
- Не редактировать `.react-router/types/`.
- SSR сохраняется: 404 отдаётся с HTTP `404`; 429/5xx route errors
  отдают соответствующий статус; защищённый контент в SSR не
  появляется.
- Root boundary не использует провайдеры и не должен импортировать
  `useTelegram`, `useAuth` или React Query.
- `requestId` не логируется и не сохраняется.
- Тесты — Vitest, окружение `node`; для презентационных компонентов
  допускается `renderToStaticMarkup` без jsdom.
- Проверки: `npm test`, `npm run typecheck`, `npm run build`.
- Незакоммиченные изменения текущего рабочего дерева не откатывать и не
  переписывать без необходимости.

## 9. Вне scope

- Ошибки валидации форм (400/422), inline-ошибки полей и toast-
  уведомления.
- Глобальный перехват 429/5xx из `apiRequest` или React Query, общий
  error overlay/context.
- Парсинг `Retry-After` и countdown до повторной попытки.
- Новый экран для network-ошибок; они используют generic `server`.
- Изменение auth-экранов `AuthScreen`, auth state machine и retry-
  последовательности `401`.
- Изменение `BottomNavigation`, главного экрана и voice-сценария.
- Добавление catch-all route и изменение `app/routes.ts`.
- Новые дизайн-токены, `dark:`-классы, новые иконки или иллюстрации.
- Haptics на error-экранах.
- Meta/noindex, аналитика и логирование ошибок.
- Backend-изменения.
- Коммиты и изменение git-истории.

## 10. Критерии приёмки

- [ ] Неизвестный URL отдаёт HTTP `404` и рендерит «Страница не найдена»
      с кнопками «На главную» и «Назад» и нижней навигацией.
- [ ] 404 доступна без авторизации.
- [ ] `ApiError`/route response со статусом 429 рендерит «Слишком много
      запросов» с «Повторить запрос», «Назад» и подсказкой «Сделайте
      небольшую паузу».
- [ ] 429 не показывает код ошибки и не парсит `Retry-After`.
- [ ] `ApiError`/route response со статусом 5xx рендерит «Что-то пошло
      не так» с двумя абзацами описания, «Попробовать снова» и
      «Назад».
- [ ] 5xx с непустым `requestId` показывает `Код ошибки: ...`; без
      `requestId` вторая строка скрыта.
- [ ] Прочие 4xx используют generic-вариант без блока «Ошибка на
      стороне сервера» и без кода.
- [ ] `throwAppError` сохраняет статус и `requestId` через
      `throw data(...)`; готовый route response пробрасывается без
      изменений.
- [ ] «Повторить» вызывает revalidation для route response/ApiError/
      ApiNetworkError и reload для остальных ошибок.
- [ ] «Назад» возвращает на предыдущий экран; без истории в приложении
      открывает `/`.
- [ ] Во время revalidation основная кнопка disabled и `aria-busy`.
- [ ] Все три экрана используют `AppShell`, светлую/тёмную палитру
      `app-*`, не используют `dark:` и не дублируют Telegram header.
- [ ] Нижняя навигация отображается на всех трёх экранах, активна
      «Главная», вкладки не навигируют.
- [ ] На 320 px нет горизонтального скролла, текст и кнопки не
      обрезаются.
- [ ] Карточка, отступы, типографика и высоты соответствуют §5
      (315/334/368 px при ширине 362 px).
- [ ] Root boundary не использует провайдеры; `_app` boundary
      сохраняет `AppProviders`.
- [ ] 429/5xx из `_app` boundary заменяют `AuthGate`, но не ломают
      auth-состояние после возврата на главную.
- [ ] DEV preview `?state=429` и `?state=5xx` показывает нужные экраны;
      в production preview не активен.
- [ ] `npm test`, `npm run typecheck`, `npm run build` проходят.
- [ ] `curl -i http://localhost:3000/does-not-exist` возвращает `404` и
      содержит тексты 404-экрана.
- [ ] SSR-ответы не содержат защищённого контента.

## 11. Принятые решения

- По решению пользователя 429/5xx показываются через route error
  boundaries, без глобального перехвата React Query/API.
- По решению пользователя нижняя навигация рендерится на всех трёх
  error-экранах, как в Figma.
- По решению пользователя под 429 показывается только «Сделайте
  небольшую паузу» в обеих темах. Dark-фрейм с «Ошибка на стороне
  сервера. Код ошибки: …» считается copy-paste-артефактом.
- По решению пользователя «Назад» использует history back с fallback
  на `/`; retry использует revalidation с fallback на reload.
- 404 обрабатывается корневым boundary, а не catch-all route: это
  сохраняет HTTP-статус и делает экран публичным.
- `_app` boundary добавлен, чтобы 429/5xx из дочерних маршрутов не
  размонтировали `AppProviders`.
- Root boundary остаётся без провайдеров; error-экраны не используют
  Telegram API и haptics.
- Для передачи 429/5xx из loader/action через SSR добавлен
  `throwAppError`, потому что обычные `Error` санитизируются в
  production.
- 5xx показывает реальный `requestId`, а не демонстрационный код из
  макета; при отсутствии кода строка скрывается.
- Вторичное действие использует `app-accent`, а не отдельный `#0088FF`
  из Figma, чтобы не добавлять новый токен.
- Карточка центрируется grid-строками `1fr`, подсказка остаётся в
  обычном потоке в зарезервированной строке ниже карточки. На коротких
  экранах третья строка переключается на `minmax(57px,auto)`, документ
  растёт и прокручивается, поэтому обычный preview-код помещается без
  прокрутки, а длинные `requestId` доступны выше нижней навигации;
  `break-words`/`max-w-full` и `min-w-0` у контейнера подсказки
  исключают горизонтальный скролл. Это соответствует макету и
  финальному review.
- DEV preview — только для ручной проверки, в production не активен.
- Ошибки валидации и auth-экраны в эту итерацию не входят.
